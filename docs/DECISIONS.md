# Decisions

Decisions made with the owner, newest last, with the reason. Change one only with the owner's agreement (contributors:
open an issue).

| Date | Decision | Why |
|---|---|---|
| 2026-11-10 | C# / .NET 10; **WinDivert** for Windows capture, not a custom WFP driver | No driver signing or WDK needed |
| 2026-11-10 | Keep **Proxifier 4 `.ppx`** import/export byte-compatible (incl. password encryption) (replaced on 2026-11-20: `.ppx` import/export dropped, the password encryption kept) | Easy migration from Proxifier |
| 2026-11-10 | Outbounds are called **tunnels**, never "proxies" (UI and code); native format `.sluice` (JSON) | Owner's terminology, like HTTP Injector |
| 2026-11-10 | Tunnel roadmap: native SSH (payload, TLS+SNI) → sing-box sidecar for SS/VMess/VLESS/REALITY/Trojan/Hysteria2/TUIC → share links/subscriptions → UDP | Covers what users of such apps expect |
| 2026-11-10 | sing-box as a **separate helper process** (GPL-3.0), one per tunnel with a local SOCKS5 inbound | Mature protocol implementations without linking GPL code |
| 2026-11-11 | SSH through **sing-box's SSH client** by default (per-connection flow control); SSH.NET as fallback, selectable per tunnel (`sshclient`) | SSH.NET suffered head-of-line blocking (one slow connection stalled others) |
| 2026-11-11 | Tunnel lifecycle: on/off switch, idle stop, health checks, retries then give up, notifications on connect/disconnect | Owner's request |
| 2026-11-13 | Ship on **Linux** too: UI ported to **Avalonia 12**, design kept identical | Cross-platform with minimal code changes |
| 2026-11-13 | **One branch, separate modules**: `Sluice.Core` shared; `Sluice.Platform.Windows` / `.Linux` behind `IPlatformServices` | Owner's choice over separate branches |
| 2026-11-13 | Linux capture with **nftables + NFQUEUE** (per-connection decision on the first SYN, like Windows); Sluice's own traffic excluded by a private group ID; fail-open queue | Same model as Windows; direct traffic never touched |
| 2026-11-13 | Linux capture **without root** via `setcap` (installer), not a root GUI | Root GUIs lose notifications and Wayland may refuse them |
| 2026-11-13 | Linux UDP through tunnels deferred (TPROXY); until then UDP of tunneled apps is blocked | Browsers fall back from QUIC to TCP, nothing leaks |
| 2026-11-14 | Linux release is **app-only** (framework-dependent); `install.sh` installs .NET 10, nftables, libcap, libraries | Small package; owner's choice over a 73 MB self-contained one |
| 2026-11-14 | sing-box for the Linux release is **downloaded by `install.sh`** (pinned, SHA-256 checked), with an offline fallback (archive next to the installer) | Owner's choice (smallest package) |
| 2026-11-14 | **No third-party binaries in git**: the build fetches WinDivert and sing-box (pinned, SHA-256 checked) into `.deps/` | Owner's request: like Maven dependencies |
| 2026-11-14 | Public history cleaned: no reverse-engineering notes, no promo material, no release artefacts, no real server or user names | Preparing to publish on GitHub |
| 2026-11-14 | Docs split by purpose (`docs/STATUS`, `REQUIRED`, `FIXES`, `FEATURES`, `QUICKSTART`, `linux/`, `windows/`); agent notes in `claude/` | Owner's request, so anyone can continue |
| 2026-11-18 | Published on GitHub; work split into **areas** (Linux, Windows, UI, Core) with forks and pull requests; an agent changes only its area's files (`AGENTS.md`); `main` holds code, tests and docs only; packaging on `release/linux` and `release/windows` (replaced on 2026-11-19: packaging scripts live on `main`), agent notes on `agent-notes`, none merged into `main` | Owner's request: platforms developed independently without conflicts |
| 2026-11-18 | **Issue dependencies enforced at merge**: a PR fixing an issue that is "blocked by" an open issue fails the required "Blocked issues" check on `main` (`.github/workflows/blocked-issues.yml`); repository checks may live in `.github/` on `main` | Owner's request: parts of a cross-area fix must land in order |
| 2026-11-18 | **Docs first, then issue, then code** (replaced on 2026-11-19, below): every fix, feature or required item gets a merged docs pull request (its entry in FIXES/FEATURES/REQUIRED or the area's docs), then an issue, then the code pull request with `Fixes #N`; an issue is checked for open blockers before work starts | Owner's request: the plan in the docs stays the source of truth and work starts only when it is free to |
| 2026-11-19 | **Issue, then one pull request** (replaces the 2026-11-18 docs-first order): every fix, feature or required item gets an issue (from a template), then one pull request with code, tests and doc updates and `Fixes #N`; a docs pull request comes first only for decisions (DECISIONS.md, a new cross-area interface, architecture); trivial changes need no issue. Issues are checked for open blockers before work starts | Owner's request: three steps per change was too much ceremony and kept two records of each item |
| 2026-11-19 | **Docs by area**: `FIXES.md` and `FEATURES.md` split into `docs/core/`, `docs/linux/`, `docs/windows/`, `docs/ui/`, each changed by its area; the shared docs (`docs/*.md`, `docs/architecture/`) may be changed by every area for its own changes; rules and decisions only with the owner's agreement | Owner's request: everyone keeps the docs true for their own work |
| 2026-11-19 | **Triage and claiming**: new issues start as `triage`; the owner triages each (and splits it into sub-issues when it needs several areas) and marks the workable ones `ready`; a contributor comments to claim one and the owner assigns them (contributors can't assign themselves in a personal repository); work starts only once assigned. Questions about the plan go in the issue, not the pull request. Labels `triage` / `ready` / `in progress` / `area: …`, a project board, and an unclaim rule (14 days without activity → unassigned, back to `ready`) | Owner's request: one person decides the split, and nobody works on an issue someone else holds |
| 2026-11-19 | **Contributors work in any area**: the area belongs to the issue (its `area:` label), not to the person; one claimed issue at a time (two while one waits for review); only issues one can test on their OS; Core only on `help wanted` issues; one area per pull request, enforced by the "Area" check; CODEOWNERS for Core, `.github/` and the rules. Replaces "one area per person" from 2026-11-18 | Owner's request: people can help where work is waiting, without conflicts |
| 2026-11-19 | **Up to date before work; a Coordination section for every split**: work starts from the latest `main`, and a branch is updated onto `main` again before its pull request and every later push. When the owner splits an issue, the parent gets a Coordination section (order, the exact interface between the parts, which files each part touches, what stays unchanged) that every sub-issue follows; changes to it are agreed on the parent first, and a pull request that departs from it isn't merged | Owner's request: two parts of one problem must not each be solved their own way, and stale branches cause conflicts |
| 2026-11-19 | **No ARM64 release for now:** v1.0.0 ships for x86-64 (Windows and Linux) only; the ARM64 package (#66) is closed as not planned and kept in REQUIRED §5 | No plan to release for ARM64 for the time being; revisit after 1.0 |
| 2026-11-19 | Sluice is licensed under **GPL-3.0-only** (`LICENSE`); bundled components are listed in `THIRD-PARTY-NOTICES.md`; contributions are under the same licence (#92) | Keeps Sluice and any redistributed fork open source, the same family as sing-box (GPL-3.0) and comparable clients; a 1.0 release needs a licence |
| 2026-11-19 | **Packaging scripts live on `main`; releases are built from tags.** Packaging scripts are code: `packaging/linux/**` and `scripts/package-linux.sh` (Linux area), `packaging/windows/**` and `scripts/package-windows.ps1` (Windows area). Built packages are never committed; CI builds them from a tag `vX.Y.Z` or `vX.Y.Z-rc.N` on `main` that matches `<Version>`. After 1.0, patch releases come from a `release/X.Y` branch cut from the tag. `release/linux` and `release/windows` are retired (#93) | Packaging couldn't be reviewed or fixed through pull requests, and a tag on `main` couldn't build a release (#74) |
| 2026-11-20 | **No Proxifier `.ppx` import or export** (replaces the 2026-11-10 `.ppx` decision): Sluice opens and saves `.sluice` profiles only, in the app and the CLI. The profile password encryption (disabled / basic / account / master) stays as it is, so existing `.sluice` files still open (#133) | Owner's request before 1.0.0: `.ppx` can't hold most of Sluice's tunnels (SSH, VLESS, Trojan…), so export left them out, and import and export are more to keep correct; no released Sluice ever read `.ppx` files, so nobody loses them |
| 2026-11-21 | **Linux packages for 1.0: the tar.gz with `install.sh`, and a `.deb` for Ubuntu** (#67). The `.deb` bundles the pinned, SHA-256-checked sing-box (unlike the tar.gz, whose `install.sh` downloads it) and depends on Ubuntu's own `dotnet-runtime-10.0`; Debian uses the tar.gz. No AppImage for 1.0 (#144): it can't hold the launcher's capture rights, and a self-installing one would only wrap `install.sh` | Owner's choice: a package installs without network access and with a fixed sing-box; the AppImage is revisited after 1.0 |
| 2026-11-22 | **Windows package for 1.0: an Inno Setup installer, self-contained** (#64). `Sluice.Desktop` and `Sluice.Cli` are published self-contained for win-x64 (the .NET runtime is inside, so nothing is downloaded during setup and the PC needs no .NET), with WinDivert and sing-box; Setup installs per machine, adds the Start Menu shortcut with the app ID "Sluice" and the firewall rules, and removes them on uninstall. An MSI built with WiX follows after 1.0 (#186). | Owner's choice: a Windows user should get a working app from one file, offline too; the larger installer is the price. Inno Setup was already used for the unreleased 0.1.0 installer |

Considered, not decided: an own **WFP connect-redirect driver** for Windows capture (as Proxifier does) instead of
per-packet WinDivert. Measurements show it isn't needed for now (docs/windows/FIXES.md §3); it would reverse the 2026-11-10
decision and needs driver signing. The owner's decision.
